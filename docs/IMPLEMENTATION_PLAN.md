## Product and customer experience

This is a carefully edited, **one-of-a-kind clothing** drop, not a static catalog or generic marketplace. Every product has one sellable physical unit. Initial categories are tops, bottoms, outerwear and dresses; add accessories only when real stock exists. The owner selected an **editorial thrift archive** direction grounded in `static/brand/dathrift-logo.png`, but must approve a concrete concept before storefront UI code. Use **Impeccable** and **ui-ux-pro-max** when shaping it. Real photos, condition/flaws and centimeter measurements must lead; clearly marked test-only fixtures are allowed in development but never as live merchandise.

Launch scope is English-first, guest multi-item cart/checkout, one unit per distinct product, and Bangladesh-only delivery. The proposed customer rates are **৳80 for eligible Dhaka-city areas** and **৳130 for other supported Bangladesh areas**, once per order. **Steadfast is the intended courier**; its official coverage is broad, but exact Dhaka-area mapping, merchant terms, off-grid exceptions and actual delivery promises remain prerequisites. Show server-verified prices/shipping before bKash; cart actions never reserve. Public browse starts with category, size, price and availability filters plus newest-first sort. Sold products stay on permanent URLs with **Sold out** and no purchase action. Customer updates use a scoped order-status page and manual staff contact, not automatic SMS/email. The canonical storefront domain is **`https://dathrift.shop`**, with `www` redirected after separately approved DNS/deployment work. Draft customer policy and SEO rules are in [Phase 7](phases/07_SEO_ACCESSIBILITY_POLICY.md); do not publish unapproved delivery/returns claims.

Products are dynamic: staff enter name, integer-BDT price, description, condition/flaws, size, clothing category, category-specific centimeter measurements and fit note, optional brand, and **1–8 photos with alt text**. No previous-price/discount feature in v1. A published slug stays permanent; typo corrections redirect. The one owner and one moderator have equal product permissions, including guarded/audited marking of an available item sold externally; there is no hard-delete action. Later both can manage fulfillment, but **only the owner** may resolve ambiguous payments/refunds after provider verification. Neither can manually mark a website order paid. Details and test gates are in [Phase 2](phases/02_CATALOG_ADMIN.md), [Phase 4](phases/04_RESERVATION.md) and [Phase 6](phases/06_STOREFRONT_CHECKOUT.md).

## Production architecture and non-negotiable invariants

- **SvelteKit on Cloudflare Workers:** `@sveltejs/adapter-cloudflare` provides server-rendered catalog/product pages, server actions/endpoints, bKash callbacks and assets. Do not ship a static-only site, public debug probe or client-side secret. Application/test/tooling source is TypeScript (`.ts`, `<script lang="ts">`); generated Worker JS is output. [Cloudflare SvelteKit guide](https://developers.cloudflare.com/workers/framework-guides/web-apps/sveltekit/)
- **D1 is the single durable primary:** product, inventory, order and payment state live in versioned SQL migrations and server-only D1 bindings. The browser sees only safe Worker responses. Prove conditional all-or-nothing multi-item reservation and external-sale races on real D1 before payment; `batch()` alone is not a correctness proof. Add Durable Objects only if evidence shows D1 needs coordination, without creating a second source of truth. The owner approved the advisory `apac` hint for the two nonproduction test databases. [D1 binding](https://developers.cloudflare.com/d1/worker-api/d1-database/) · [D1 data location](https://developers.cloudflare.com/d1/configuration/data-location/)
- **R2 holds product files and separate D1 exports:** product image objects are not database rows; store ordered references/alt text in D1. A distinct private backup bucket holds hourly copies for 48 hours and daily copies for 30 days, with stale/failure alerts to the owner's email. D1 Time Travel is additional protection; R2 in the same Cloudflare account is not cross-provider disaster recovery. A product-image bucket is **not** covered by Phase 1 resource approval. [D1 backup/export guidance](https://developers.cloudflare.com/d1/reference/time-travel/)
- **Cloudflare Access protects staff admin:** the planned hostname is `admin.dathrift.shop`. Exact owner/moderator Google emails are allowlisted, with **independent Access MFA**; Worker-side identity/authorization must also reject alternate `workers.dev`/preview paths. Better Auth is not needed for this two-person v1 team. The owner will place local values in ignored `.env.local`; deployed Access policies and Worker secrets are configured separately. The owner alone manages staff Access membership. [Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) · [independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/)
- **bKash PGW remains server-side:** use the actual merchant product/version; validate invoice, BDT amount, payment/transaction IDs and final provider status. A browser redirect never proves payment. One product belongs to at most one live reservation or paid order. Ambiguous payment retains stock for **owner-only** reconciliation, not auto-release; network calls remain outside D1 transactions. No live merchant-account change or checkout enablement without specific approval.
- **PocketBase code is removed; its Git history is spike evidence only:** Cloudflare Containers' writable disk is [ephemeral](https://developers.cloudflare.com/containers/faq/) and [R2 FUSE is not fully POSIX-compatible](https://developers.cloudflare.com/containers/examples/r2-fuse-mount/), so PocketBase SQLite is retired from the production path. D1 migrations are the only active database source.
